**当前不开发新的质量工具，不修改现有 Skill/Pipeline，不重新评分或训练。** 下一步的最小价值是：先取得 Owner 对“仅使用既有十案、有限只读机制核查”的单独批准；获批后核查重复来源及四臂共同性，形成可归因或不可归因的事实结论。未获批前，本文件只是修订后的方向性建议。

- P2 旧五条 Quality-v1 候选的身份/Reviewer 定位已对齐；可信来源版本、训练输入上下文合同、世界组件与隔离、严重标记补充筛查、Reviewer 独立性及 Owner 批准等证据仍不完备。**Quality-v1 不要求历史生产 Provider 请求字节级精确回放**。如果采用明确批准的离线训练上下文，必须证明其来源合法、构造与版本可复现、世界/人物适用性及隔离；只在声称历史目标时点精确输入时，才额外要求相应历史版本和时序证据。`OWNER_EVIDENCE_HOLD`；不能凭 Stage v2 结构 PASS 或 Autolink 升级准入。

## 二、三个关键挑战的修订结论

1. **重复存在，不等于 R60 微调致因。** 首要交付改为逐案识别历史 Assistant 文本复制、本轮内部循环、生成截断影响，以及同一题 Base/R46/R54 是否也出现相似现象。可多标签；无法判定则记 `UNATTRIBUTABLE`。只凭定向选例不能估算 R60 相对对照的整体重复发生率，更不能直接归因于训练数据。
2. **篇幅不足首先是评估合同的可行性问题。** 四条明确篇幅要求未满足且 R54 也未满足；冻结 `max_new_tokens=2048` 与目标中文字数是否兼容，需要在未来评估冻结前检查。当前只能标记“预算可能影响评估解释”，不能将四条直接计为 R60 特有退化，也不得事后修改原题、参数或 Judge 分数。
3. **P2 证据门禁与历史请求精确回放分离。** 对所选择训练输入合同，应分别核实合法源文本及版本、明确可复现的上下文（历史快照或已批准离线编排）、世界与人物适用性、保护集隔离、Review/Owner 证据。若额外主张“真实历史目标时点的原始输入”，才需要对应版本与时序的加强证明；不能把该要求无条件施加给合法的离线训练上下文。既有五条目前仍因多项真实证据缺失而 HOLD。

## 四、评审解释口径（建议，不改变既有代码和评分）

这些判定口径已落在现行 SFT Skill 所要求的“重复表达、NPC 主动推进、玩家自主权、严重问题 HOLD/REJECT”范围内；本轮仅补充审阅时应遵循的解释，不另建评分体系。

1. **玩家明示行为**：用户已经指定的玩家动作、台词与决定，模型可适度承接和展开；但扩写不得与用户意图矛盾，也不能额外替玩家确立关键选择。
2. **NPC 自主推进**：NPC 可以主动说话、提问、改变自身行动、创造事件和施加外部压力；不能为了推进而将玩家的自愿接受、心理认同或不可逆选择写成既成事实。
3. **NPC 强制与玩家自主权**：NPC 在故事中企图控制玩家，不自动等于模型“代玩家决定”；应检查是否剥夺玩家合理的反应窗口、是否违反已确认硬规则。严重性不能仅由动作强弱推出。
4. **安静场景**：玩家明确选择离开、拒绝或沉默时，NPC 的克制与等待可属合格互动，不应因为缺少冲突或额外事件就机械判为 NPC 失败。
5. **历史回放**：逐字重放上一轮长段、回退剧情进度、在单轮回复中循环同一片段且不产生有效新状态，应单独记作可复核的生成异常；与文学重复修辞区分。
6. **证据争议**：把“用户原话”误当模型新创玩家动作、只凭一个 Judge severe flag 而缺少可定位原文、或者存在正当场景解释时，保留 `UNCERTAIN/HOLD`，不得自动 REJECT，也不得自动改为 PASS。

## 五、最短执行路径（不重复工作）

### 步骤 A：Owner 明确批准仅限十案的只读机制核查（下一授权节点）

请 Owner 仅对步骤 B 的**有限、只读、不得新增生成或模型调用**作单独明确授权。用户对方案的方向性讨论和文字修订，不自动构成该操作的授权；也不等于 Owner 已独立复审 10/10。是否采用未来评审解释性示例与代码/Skill 改动均另行决定。

### 步骤 B：已选十案的有界只读机制检查（待授权，首要交付）

**不新建算法/工具、不扩大为 Gold48 全量人工复审。** 仅用现有 P1 冻结 10 案包与可读 metadata，对原定 3 条重复/回放重点案例及同输入四臂作一轮检查；其余 7 案只在已有事实涉及同类机制时引用，不再扩样：

- **来源与形态：** 每条标记 `HISTORY_COPY`（旧 Assistant 原文长段复制）、`WITHIN_OUTPUT_LOOP`（本轮内部循环）、`TRUNCATION_AFFECTED`（因输出结束影响完整性）、`CROSS_ARM_SHARED`（同题对照臂也出现相似问题）、`UNATTRIBUTABLE`（无法归因）中的适用项，允许多标签；每个判断以私有原文定位或现成 `finish_reason` 为依据。
- **四臂比较：** 针对同一道题的 Base、R46、R54、R60，核对是否各自出现回放、循环、状态更新缺失或长度问题；若四臂现象共同存在，不能归因于 R60 特有微调。即便只有 R60 出现，也只能称“这次生成中的 R60 特有现象”，不是训练因果证明。
- **预算交叉核查：** 对已有篇幅争议检查用户最低字数要求、当前回答字数/已有 token 元数据、`length` 或 EOS 结束情况与固定 2,048 token 上限。不从字数直接推断 token，缺少实际元数据就标记 `UNVERIFIED`。
- **固定交付：** 每个案例仅给出原因类别、对照臂共同性、可确认事实和未解决假设；对无证据机制输出 `UNATTRIBUTABLE`，不强制五选一。普通交接只传 SAFE 聚合，不输出原文、Case 身份或 SHA。

若 P1 包已有足够证据即直接复用，缺什么就记未验证；绝不重建生产 Ledger、重查 R50 或重跑模型。

### 步骤 C：仅形成条件式、最小改进选项

- **若在已选同题案例中回放主要出现在 R60**：只能登记“此选例的 R60 独有症状”，不能据此估算总体频率或锁定 SFT 根因。未来可提出独立样本下的重复行为验证或训练样例内容抽查，但需另行授权。
- **若四臂共同受篇幅预算约束**：先将现有情况登记为**评估合同可行性限制**，未来应在题目与 `max_new_tokens` 冻结之前检查可行性；不得改写已冻结 Gold48 输入或事后扩大当前输出预算。
- **若主要来自 Judge 边界误判**：先修订**未来**审核指南中的示例和争议升级说明；现有 478 份评分、双 Judge 身份、缺失和修订仍按原冻结协议存档。
- **若有效 NPC 推进仍低**：仅提出下一阶段可操作的数据/目标行为假设，如“NPC 自主行动带来可感知状态更新，同时保留玩家选择窗口”；不要直接宣称现有训练集缺失该模式。

### 步骤 D：未来独立验证的前置条件（不是本次执行）

任何下一轮正式实验都需 Owner 另行授权，并满足：新独立来源及合法使用许可、Story/世界组件隔离和保护集元数据排除、与训练/调参题分离、对比输入冻结和四臂同口径、**冻结前核实篇幅/响应格式任务在 token 预算内的可行性**（需要模型特定 token 核验时复用现有 HF CPU 核心）、事先约定主要指标/停机条件及 Reviewer 争议处理。先预注册案例与评估口径，再采样/评分。保留 Session 聚类、不完整评分和多重比较的限制。**Gold48 已暴露用于诊断，不能包装为全新隐藏 Held-out。**
