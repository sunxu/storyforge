# 首批 R58 真实数据 Pilot（待正式授权）

## 优先使用现有数据，不创作新故事
1. 用 `02_story_shortlist.sql` 私有列出高活跃已审核的 V2 故事（只作发现，不等于质量保证），补充旧 SFT 与开发集的来源暴露计数，筛掉受保护世界。
2. 先划分至少 4 个潜在最终测试世界组件且保持未查看消息内容；其余世界进行 Train/Val 分组，**不得按单条回复随机切分**。
3. 先选约 20–30 个不同训练/验证世界，按不同题材、情节、人物结构均衡；每个世界拟初筛 5–8 条真实完成回复，共约 100–200 条。
4. 自动结构检验后，独立 Reviewer 对优先级高的 60–100 条进行第一次质量审核；受理数量以真实 PASS 为准，不凑配额。
5. 使用高质量 Teacher 修复一部分明确错误的目标（建议首轮最多占最终 Train 的 20%，只进 Train），对同样输入进行 2–3 候选排序，避免新造与世界不符的情节。
6. Owner 对逐案签核的结果、真实世界语义映射和训练变量给出确认；严格执行 source hash、last Assistant label mask、边界验证和 HF CPU 工具预检。
7. 验证达到合理世界覆盖及质量后，在固定 CPU/GPU 执行计划获独立批准时才开始 v0.4 Datafix 训练；另留受保护的新独立评估集。

## 候选的建议权重（不是最终质量评分）
- 40% 自然文学与剧情连续性；25% 玩家自主权；20% NPC 主动推进；15% 硬规则/人物关系。
- 评分应避免“短回复就安全”或“长回复就有文学性”的简化；高活跃也不是高质量。
- 每世界设最大贡献比例，优先多世界覆盖；保留多标签和 Reviewer 理由，禁止只保留总分。

## Teacher 的对照实验
对齐同一基本模型、同一 System 和相同评估输入，可准备两种数据版本：`v0.4-original-only` 与 `v0.4-original-plus-teacher`。唯一主要变化是 Teacher 审核通过的监督目标及其数量，训练步数/Token 规模差异明确披露。**不要先用未曝光最终测试集挑 Teacher 候选**。
